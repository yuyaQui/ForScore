# サイバーパンク・デザインシステム（Main / Admin 共通）

2nd Round の Main画面(`MainSecondRound.tsx`)・Admin画面(`AdminSecondRound.tsx`)を作る過程で
固めた、見た目に関する共通の技法・部品・判断をまとめたもの。**次のラウンド（3rd Round 以降）の
デザインに着手するときは、まずこのファイルを読んでから始める。** 個別の色や座標のような細部を
毎回作り直すのではなく、ここに置いた共通部品を再利用してラウンドごとの見た目を統一する。

関連ファイル:
- `lib/cyberpunkCard.ts` — 色・clip-path・文字の縁取りなど、見た目計算の共通関数
- `lib/ordinal.ts` — 序数表記(`1st`/`2nd`/...)
- `app/components/FixedStage.tsx` — Main画面用の 1920×1080 固定キャンバス＋自動拡大縮小
- `app/components/LightningBolts.tsx` — 電撃エフェクトのSVG（縦長・横長の2種）
- `app/globals.css` の `@keyframes boltFlicker` — 電撃の明滅アニメーション
- Design アーティファクト本体（Cowork Design: 2nd Round、および PDFコメント）— 元の見た目の
  仕様そのもの。細かい寸法や色の"なぜこの値か"の経緯はこちらのコメントに詳しい

## 1. カラー・順位帯（tier）システム

`lib/cyberpunkCard.ts` の `tierOf(paperRank, accent)` が、1st Round のペーパー順位から
その選手の枠色を返す。境界は `lib/advantage.ts` の連答権アドバンテージの区分（4位/12位/24位）と
意図的に一致させてあり、「画面の色 = アドバンテージの区分」を選手・観客が直感的に対応づけられる
ようにしている。区分を変えるときはアドバンテージ側の区分も一緒に見直すこと。

| 順位帯 | 色 | 備考 |
|---|---|---|
| 1〜4位 | 赤 `#FF3B5C` | |
| 5〜12位 | `ACCENT`(既定 `#2F7BFF`) | 見出し下線と同じ色。`ACCENT` を変えると自動で連動する |
| 13〜24位 | 黄 `#FFC93C` | |
| 25〜48位 | 緑 `#35FFA0` | 2nd Round の見出し下線も同じ緑 |
| 49位〜 | 紫 `#B98BFF` | 2026-10-11 追加（`TIER_PURPLE`）。Extra Round の見出し下線も同じ紫 |

`ACCENT` はデザインシステム全体のアクセント色（見出し下線、5〜12位帯の色）としてラウンドを
またいで統一する。ラウンドごとに変える理由がない限りこの値のまま使う。

**GUNMETAL_DARK と GUNMETAL_MID の使い分け（要注意）**: Quiz View のカード枠は
`GUNMETAL_DARK`(`#1D1F20`、黒に近い)、Turn Over のカード枠は `GUNMETAL_MID`(`#3A3F46`、やや
明るいグレー)を使う。本来は統一したいところだが、Design アーティファクトの制作過程で Quiz View
側だけ「黒に近づける」調整が何度か入り、Turn Over 側は調整前の値のまま残っている。実装は
「アーティファクトと実装後の画面を変えない」方針のため、統一せずこの食い違いをそのまま持ち込んで
いる。次にどちらかを調整するときは、もう片方も揃えるかどうかを含めて検討すること。

## 2. clip-path による八角形／斜めカットの枠

カードの枠は単純な矩形ではなく、角を斜めにカットした多角形。実装は3つの関数に分かれる。

- `OCTAGON_CLIP_PERCENT` — Quiz View（縦長カード）用。**パーセンテージ指定**なので、登場
  アニメーションで高さが変わっても1つの定数のまま歪まない。
- `buildTopBottomCutClip(outerW, outerH, cutPad)` — 外側の八角形からさらに内側に
  `cutPad` だけ入った位置に対応する頂点を打ち、外側⇄内側の頂点を斜めにつなぐことで「額縁の
  縁だけ色付きに見える」ガンメタルの重ね(cut)を作る。**縦方向**(上下)に頂点を打つ版。
- `chamferClip(w, h, chamfer)` — Turn Over（横長カード）用。四隅を均等に(既定16px)斜め
  カットした八角形。**ピクセル指定**なので、幅が変わる（collapsed⇄expanded）たびに
  `clip-path` 自体もあわせてトランジションさせないと瞬時にスナップする（後述）。
- `buildSideCutClip(w, cardH, cutPad, chamfer)` — `buildTopBottomCutClip` の横長版。
  Turn Over のカードは高さが伸縮しないため、変化するのは幅(w)だけで、Y座標は固定でよい。
  左右の辺だけ色付きが見える。

**ピクセル指定のclip-pathを幅・高さのアニメーションと連動させるときの注意**: `clip-path` は
既定では他のプロパティと連動せず、幅や高さが変わった瞬間に新しい形へ瞬時にスナップする
（Turn Over の実装で最初にハマった点）。`width`/`height` のトランジションと**同じ
duration・delay** を `clip-path` にも指定して、見た目の縁の動きを実際の箱のサイズ変化と
同期させる。パーセンテージ指定の `OCTAGON_CLIP_PERCENT` はこの問題自体が起きない
（親のサイズに対する相対値なので、サイズが変わっても自動的に正しい形になる）ので、今後
新しく作るカードでも高さ／幅がアニメーションするなら、可能な限りパーセンテージ指定を優先する。

## 3. CJK文字の縁取り（outlineShadow）

`outlineShadow(color, w)` は、漢字・かな交じりの文字に「本当の輪郭線」の縁取りを付けるための
`text-shadow` 文字列を生成する。同じ色のコピーを円状に14方向へ `w`px オフセットして重ねる
「太らせ」方式。`-webkit-text-stroke` は画数（サブパス）ごとに縁取ってしまうため、複数画数から
なる漢字では画数の間に隙間が空いてしまう。この方式なら文字全体の外形をなぞった縁取りになる。

縁取りの色は `shade(tier.color, -0.35)` で、その選手の順位帯の色を少し暗くしたもの。白文字
(`#F3FAFF`など)の視認性を保ちながら、順位帯の色と連動させている。

## 4. 電撃（lightning）エフェクト

カードの登場・展開時に一瞬走る、不規則なジグザグ線が非同期に明滅するエフェクト。
`app/globals.css` の `@keyframes boltFlicker`（不透明度が `1 → .35 → 1 → .5 → 1` と明滅する
だけの単純なキーフレーム）を、`app/components/LightningBolts.tsx` の各 `<path>` が
微妙に異なる `animation-duration` / `animation-delay` / `steps()` で使うことで、8〜16本の線が
バラバラに明滅しているように見える。

- `LightningBoltsVertical` — Quiz View（縦長カード）用。viewBox `0 0 64 150`、8本。
- `LightningBoltsHorizontal` — Turn Over（横長カード）用。viewBox `0 0 150 150`、16本。

どちらも `preserveAspectRatio="none"` で親の `div` いっぱいに引き伸ばすため、親のサイズが
アニメーションで変化すれば電撃自体もそれに追従して伸び縮みする。新しいラウンドで別の形の
カードに電撃を使う場合、線の座標は使い回さず新規に作るか、既存2種のどちらかを流用するかを
判断すること（座標を機械的に引き伸ばすと不自然になりやすい）。

## 5. カード列がはみ出すとき: 列ごと transform:scale() で縮める

Quiz View の12枚のカードを横一列に並べる部分で、Design アーティファクトの検証時
（モックデータ8名）は画面内に収まっていたが、実際の1組の人数(12名)では合計幅が
画面の余白を引いた横幅を超え、両端のカードが画面外に見切れる不具合が起きた
（2026-09-26 修正）。

**原因**: アーティファクトのモックデータの人数と、実際にその画面が表示する最大人数が
食い違っていた。カード1枚の幅・間隔は「8名なら収まる」前提の値のままだった。

**対処方針**: 個々のカードの寸法・文字サイズ（＝アーティファクトが決めた見た目）は
一切変えず、カードを並べた行 **全体** を `naturalRowW`(実際の人数で計算した自然な
合計幅) と `STAGE_CONTENT_W`(実際に使える横幅) の比率で `transform: scale()` する。
人数が少なく収まる場合は `scale = 1` のまま、アーティファクトと完全に同じ等倍表示になる。
`MainSecondRound.tsx` の `QuizView` を参照。

新しいラウンドで「1行に並べる枚数が本番のデータ件数に依存するカード」を作るときは、
**モックデータの件数ではなく、実際に起こりうる最大件数で必ず収まるかを計算してから**
実装する。収まらない可能性があるなら、最初からこの「行ごと scale」の仕組みを組み込んでおく。

## 6. FixedStage: 1920×1080 固定キャンバス＋自動拡大縮小

**経緯・決定事項（2026-09-25）**: Design アーティファクトは 1920×1080 の固定キャンバスを
前提に、細かい座標をすべて px 単位で作り込んである。これを実際の画面（vw/cqw 相対単位）に
変換し直すと、見た目がアーティファクトから微妙にズレるリスクが高く、変換の手間も大きい。
そこで、会場のスクリーンは**常に16:9で運用する**という前提を確認した上で、
「1920×1080 の固定キャンバスをそのまま作り、実際のウィンドウ／モニターのサイズに合わせて
`transform: scale()` で拡大縮小する」方式（案A）を採用した。この方式は2nd Round に限らず、
**今後の全ラウンドの Main画面に共通で使う**。

実装は `app/components/FixedStage.tsx`。`position: fixed; inset: 0` で常にビューポート全体を
覆い、`ResizeObserver` で実際の表示領域のサイズを監視し、`Math.min(width/1920, height/1080)`
を `scale` として内側の 1920×1080 の `div` に適用する。万一16:9からズレた画面で表示しても、
小さいほうの比率を採用しているので中身が画面からはみ出すことはなく、上下または左右が黒く
余るだけになる（レターボックス）。

新しいラウンドの Main画面を作るときは、その画面のトップレベルを `<FixedStage>` で包み、
中身は 1920×1080 を前提にした px 単位の座標でそのまま組む。vw/cqw への変換は不要。

## 7. Admin画面: 線形フローUIのパターン

**経緯・決定事項（2026-09-25）**: 実際の大会本番の進行は「1組目発表→1組目クイズ→2組目発表→
…」のように、トラブルがない限り後戻りしない一本道。これに対し、Admin画面に組・画面表示を
それぞれ独立に切り替えられるボタン群を並べる作りは、「今どのボタンを押すべきか」を進行役が
毎回考える必要があり、本番の緊張感の中では事故のもと。そこで `AdminSecondRound.tsx` では、

- **状態から「次に押すべきボタン」を1つだけ機械的に決めて大きく表示する**（プライマリ導線）。
  例: `turnOverPhase==='collapsed'` なら「◯位を発表 ▶」、`expanded` かつ最終ステップ未満なら
  「次へ ▶」、最終ステップの `expanded` なら「クイズ開始 ▶」、クイズで全員の正誤が確定したら
  「◯組目へ進む ▶」（4組目終了後は押せない「2nd Round 終了」表示に切り替え）。
- **個別の組・画面切り替えボタン、Reset/Undo は `<details>` で折りたたんだ「手動操作
  （トラブル時のみ）」の中に退避する。** 普段は見えないが、巻き戻り等の想定外対応が必要に
  なったときにいつでも開ける。

この「状態から次の1手だけを提示する」パターンは、後戻りがほぼ発生しない一本道の進行を持つ
他のラウンド（3rd Round のコース進行など）にも当てはまる可能性が高い。該当するラウンドの
Admin画面を作るときは、まずこのパターンが使えないか検討する。

## 8. 新しいラウンドのデザインに着手するときのチェックリスト

1. `lib/cyberpunkCard.ts` の色・clip-path・縁取り関数をそのまま import して使う（色や
   数式を独自に再定義しない）。ラウンド固有のカード形状が必要なら、ここに関数を追加する形で
   拡張し、他ラウンドから見えないラウンド専用ファイルには置かない。
2. Main画面は `FixedStage` で包み、中身は 1920×1080 の px 座標で組む。
3. 電撃エフェクトが要るカードは `LightningBoltsVertical` / `LightningBoltsHorizontal` を
   再利用するか、同じ考え方（`boltFlicker` キーフレーム＋バラバラな delay/duration）で新規に
   作る。
4. 進行がほぼ一本道なら、Admin画面は「次の1手だけを大きく提示し、個別操作は折りたたみに
   退避する」パターンを検討する。
5. Design アーティファクトと実装後の画面を見比べ、意図的な差分（今回の GUNMETAL_DARK /
   GUNMETAL_MID のような）があれば、その理由をこのファイルに追記する。
