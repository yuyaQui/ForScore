# 3rd Round: Number 10 設計メモ

20名 → 8名。誤答ルールの異なる4コースに5名ずつ振り分け、各コース2名が準決勝に進出する。

このメモは実装前の設計合意を目的とする。ルールの出典は `abc the24th ルール` の 3rd Round 節。

---

## 1. 全体の流れ

3rd Round は性質の異なる2つのフェーズで構成される。

```
[フェーズ1] コース選択  ── 抽選とエントリーを4回繰り返す
    抽選(1回目) → 1番目のコース確定 → エントリータイム → 出場者5名確定
    抽選(2回目) → 2番目のコース確定 → エントリータイム → 出場者5名確定（残り15名から）
    抽選(3回目) → 3番目のコース確定 → エントリータイム → 出場者5名確定（残り10名から）
    抽選(4回目) → 4番目のコース確定 → エントリータイム → 出場者5名確定（残り5名）

[フェーズ2] クイズ実施
    実施順に従って1コースずつ、5名の早押しクイズ
    各コース2名勝ち抜け × 4コース = 8名
      ↓
    通過順位を確定 → 準決勝の席順に変換
```

**20名全員の所属が決まってから、クイズが始まる。** 「1番目のコースを決めてすぐ実施」ではない。

**抽選は4回に分けて行う。** 一度に4コース分の順序を決めるのではなく、その場で1つずつ引く。2回目は残り3コースから、3回目は残り2コースから、4回目は残り1つなので抽選の余地がない。

## 2. フェーズ1: コース選択

### 2.1 コース実施順の抽選

コースの実施順はシステム上で抽選する。Main 画面にルーレット風の演出を出す。

#### 1回の抽選で1コースだけ決める

```
1回目: playOrder が null の4コースから1つ引く → playOrder = 1
2回目: 残り3コースから1つ引く                → playOrder = 2
3回目: 残り2コースから1つ引く                → playOrder = 3
4回目: 残り1コース（抽選の余地なし）          → playOrder = 4
```

確率的には「最初に4つまとめてシャッフルして順に開示する」のと同じだが、**その場で引く方が公平に見え、進行の実態にも合う**。

この方式なら「開示済みかどうか」を別途持つ必要がない。`playOrder` が入っていること自体が、そのコースが公開済みであることを意味する。

確定した順序は `ThirdRoundCourse.playOrder` に保存する（準決勝の席順計算に必要なため、永続化が必須）。

#### 設計上の要点: 乱数はサーバで引く

**クライアント側で乱数を引いてはいけない。** Main と Admin、複数の投影端末がそれぞれ乱数を引くと、画面ごとに違う結果が表示される。

```
1. Admin が「抽選する」を送信
2. サーバ（API）が残りコースから1つ引き、playOrder を保存する
3. 結果を Socket で全クライアントへ配信
4. 各クライアントは「配信された結果」に向かうアニメーションを再生する
```

アニメーションは結果を演出するだけで、結果を決めない。ここを取り違えると本番で表示が食い違う。

シャッフルには Fisher-Yates を使い、`sort(() => Math.random() - 0.5)` は使わない。後者は比較関数の呼ばれ方がソート実装に依存するため出現確率が偏る（24万回試行で最大352%のずれを確認済み）。

#### 段階的に作る

1. **第1段階**: 抽選して結果を即座に表示する（演出なし）
2. **第2段階**: ルーレットのアニメーションを載せる

第1段階だけでも進行は成立するため、演出は後から足せる構造にしておく。

#### やり直し

抽選のやり直しは「**リセットして最初から**」とする。全コースの `playOrder` を null に戻す。

途中まで進んだ状態があるため、「引き直す」ではなく全体をリセットする形が分かりやすい。確認ダイアログを出し、API 側でも `force: true` を要求する（画面のダイアログは API を直接叩かれると素通りするため）。

**注意:** すでに出場者が割り当てられている状態でリセットすると、所属コースと実施順が矛盾する。リセット時は `Player.thirdRoundCourseName` もあわせてクリアする必要がある。コース選択機能の実装時に対応すること。

### 2.2 優先順位

コース選択における「優先順位」は **2nd Round の勝ち抜け順 → 1st Round 順位** で決まる。

各組から5名ずつ勝ち抜けるため、2R1位通過が4名、2位通過が4名…と並び、同順位内を1R順位で解決する。2R通過順が絶対優先で、1R順位は同着時のみ効く。

実装上は既存のソート条件をそのまま使える。

```ts
players
  .filter(p => p.secondRoundRank >= 1)
  .sort((a, b) =>
    a.secondRoundRank !== b.secondRoundRank
      ? a.secondRoundRank - b.secondRoundRank
      : a.paperRank - b.paperRank
  );
```

### 2.3 出場者の決定

エントリータイム終了時点でネームプレートを掲げていた人を「挑戦の意思表示をした人」とみなす。**終了時点のスナップショットのみ**を見る（途中の上げ下げは無効）。

| 掲げた人数 | 出場者の決め方 |
|---|---|
| 5名以上 | 掲げた人のうち、優先順位**上位**5名 |
| 4名以下 | 掲げた人は全員確定。不足分は、掲げなかった人のうち優先順位**下位**から補充 |

この非対称性が制度の肝である。人気コースには上位者が入り、不人気コースには下位者が押し込まれる。優先順位が高いほど「行きたいコースに行ける」かつ「行きたくないコースを避けられる」という二重の利得になる。

### 2.4 割当アルゴリズム

```
入力: 未割当プレイヤー（優先順位でソート済み）, 掲げた人のIDリスト
出力: 出場者5名

1. raised   = 未割当のうち掲げた人（優先順位順）
2. notRaised = 未割当のうち掲げなかった人（優先順位順）

3. if (raised.length >= 5)
       return raised.slice(0, 5)              // 上位5名
   else
       const shortage = 5 - raised.length
       const forced = notRaised.slice(-shortage)   // 末尾＝優先順位下位
       return [...raised, ...forced]
```

### 2.5 進行と入力

エントリータイム中、**システムは判定に関与しない**。

#### エントリータイムのタイマーは作らない

10秒の計測は**専用BGMで行う**。システム側にもう1つ時計を持たせると、BGMと画面のカウントダウンがずれたときに、会場から見てどちらが正なのか分からなくなる。

代わりに Admin に「**エントリー締切**」ボタンを置く。BGM が終わったらスタッフが押し、その瞬間にチェック欄が開く。

- 締切前: チェック欄はグレーアウトして操作できない
- 締切後: チェック欄と確定ボタンが有効になる

締切前の入力を受け付けない作りにするのは、ルールが「終了時点で掲げていたか否か」だけを見ると明記しているため。運用上もカウントダウン中に入力する場面はない（締切後もプレートは掲げられたままで、スタッフはそれを見て入力する）。

#### 入力から確定まで

- Main 画面: コース名 / 3rd Round 参加者20名
- 締切後、Admin で「掲げていた人」にチェックを付ける
- 上位5名の選抜と下位からの強制補充は **システムが計算する**

スタッフが入力するのは「誰が掲げていたか」の事実のみ。優先順位の暗算をさせない。

確定後は同じ画面に出場者5名を表示し、**「掲げた」と「強制出場」を区別して出す**。割当が正しいかをスタッフがその場で検算できるようにするため。

#### エントリーと確定は同じ画面

締切・チェック入力・確定・結果表示をすべて1画面で行う。画面遷移を挟まない分、操作が減る。

「確定済みかどうか」は状態として持たず、**そのコースに割り当て済みの選手が5名いるか**で判定する。フラグを別に持つとデータとずれる余地が生まれる。

## 3. フェーズ2: 4コースのルール

### 3.1 一覧

| | 勝ち抜け | 誤答時 | 失格 | 判定基準 |
|---|---|---|---|---|
| **10 up-down** | 10pt 先取 | ポイントが **0に戻る** | 2誤答 | ①ポイント多い順 ②プレーオフ |
| **Freeze 10** | 10問正解 | 通算誤答回数 × 1問 **休み** | **なし** | ①正解数多い順 ②誤答数少ない順 ③プレーオフ |
| **Swedish 10** | 10問正解 | 正解数に応じ **× が加算** | × が10以上 | ①正解数多い順 ②×少ない順 ③プレーオフ |
| **10 by 10** | 総合pt **≥ 100** | 誤答ptが **1減る**（初期10） | 6誤答 | ①総合pt多い順 ②プレーオフ |

### 3.2 10 up-down

- 1問正解で 1pt、10pt 先取で勝ち抜け
- 誤答すると**現在のポイントが0に戻る**
- 通算2回誤答で失格

判定基準①は「終了時の**ポイント**」であり、累計正解数ではない。誤答直後に時間切れになった選手は 0pt で判定される。したがって**累計正解数を保持する必要はない**。

### 3.3 Freeze 10

- 10問正解で勝ち抜け
- 誤答すると「通算の誤答回数 × 1問」の間休み（1度目の誤答で1問休み、2度目で2問休み …）
- **失格が存在しない**

| 誤答 | 休む問数 | 累計 |
|---|---|---|
| 1回目 | 1問 | 1問 |
| 2回目 | 2問 | 3問 |
| 3回目 | 3問 | 6問 |
| 4回目 | 4問 | 10問 |
| 5回目 | 5問 | 15問 |

**スルーも1問として数える。** これはこのコース固有の要件で、進行UIに影響する。

**スルーを記録するのは Freeze 10 だけ。** 他の3コースではスルーが何にも影響しないため、記録しない。したがって Admin のボタン構成を**コース別に出し分ける**（スルーボタンは Freeze 10 のときだけ表示する）。

スルーは「問題が1問終わった」というイベントであり、選手個人に紐づく値ではない。DB に「スルー回数」を持つ必要はなく、残り休み問数を減らす契機として使うだけでよい。

#### 休みのモデル

各選手が「残り休み問数」を持つ。

1. 1問が終わるたび（正解・誤答・**スルー**のいずれでも）、休み中の選手の残り問数を1減らす
2. 誤答した選手は、その時点の通算誤答回数を残り問数にセットする
3. 残り問数が1以上の選手は解答権を持たない

**注意:** 誤答したその問題自体は休みに数えない。「1度目の誤答で1問休み」は次の1問を休む意味である。誤答処理でセットした直後に同じ問題で減算すると、休みが1問ずれる。

実装順序は「①その問題の休みカウントを全員分減らす → ②今回の正誤を反映する」とする。

### 3.4 Swedish 10

- 10問正解で勝ち抜け
- 誤答すると、**その時点の正解数**に応じて × が付く
- × の合計が10以上で失格

| 誤答時の正解数 | 付く × |
|---|---|
| 0 | 1× |
| 1〜2 | 2× |
| 3〜5 | 3× |
| 6〜9 | 4× |

正解が進むほどペナルティが重くなる。正解数10は勝ち抜け済みなので、表に存在しなくてよい。

失格までの誤答回数は**最短3回**（毎回4×）、最長10回（毎回1×）。最短ケースが「3名失格で終了」と同じ回数なのは偶然の一致である。

### 3.5 10 by 10

- 「正解ポイント: 0」×「誤答ポイント: 10」＝「総合ポイント: 0」から開始
- 正解で正解ポイント +1、誤答で誤答ポイント −1
- **総合ポイント（両者の積）が100以上で勝ち抜け**
- 通算6回誤答で失格

```
総合pt = 正解数 × (10 − 誤答数)
```

PDF の例「4問正解・2問誤答 → 4 × 8 = 32」と一致する。

| 誤答 | 誤答pt | 勝ち抜けに必要な正解数 |
|---|---|---|
| 0 | 10 | 10問（10×10=100） |
| 1 | 9 | 12問（12×9=108） |
| 2 | 8 | 13問（13×8=104） |
| 3 | 7 | 15問（15×7=105） |
| 4 | 6 | 17問（17×6=102） |
| 5 | 5 | 20問（20×5=100） |
| 6 | 4 | 失格 |

誤答0〜5回のどの状態からも勝ち抜けに到達可能であることを確認済み。総合ポイントは正解数と誤答数から**導出できる**ため、列として保持しない。

## 4. 共通ルール

### 4.1 終了条件

| # | 条件 | 処理 |
|---|---|---|
| 1 | 2名が勝ち抜けた | そのコース終了 |
| 2 | 3名が失格した | 解答席に残っている全員を勝ち抜けとする（順位は判定基準 → 同点なら席順。4.3 参照） |
| 3 | 15分経過 | 勝ち抜けが2名未満なら判定基準で順位決定 |

条件2は 2nd Round の「7名失格」と**同じ構造**である。勝ち抜け w 名・失格3名なら残りは `5 − w − 3 = 2 − w` 名で、これは残り枠数と一致する。したがって 2nd Round と同じ `残り人数 === 残り枠` という式で表現できる（勝ち抜け未確定の範囲で両者が一致することを確認済み）。

**Freeze 10 には失格が存在しない**ため、このコースだけ条件2が発生しない。終了条件は1と3のみ。

### 4.2 15分タイマー

- 司会の発言や拍手も制限時間に含む
- **勝ち抜けまたは失格が出たときのみ時計が止まる**（自動停止）
- 疑義の申し立て時などは手動で一時停止する
- 15分経過時点で読まれていた問題は、正解・誤答・スルーが確定するまで有効

1st Round のタイマーと異なり、**停止条件がスコア更新と連動する**。自動停止と手動停止の両方を実装する。

#### 0秒到達はコースの終了ではない

タイマーが0になっても、**正解 / 誤答 / スルーの操作は受け付け続ける**。「最後に読まれていた問題」が確定するまで進行が続くためである。

したがって、

- 0秒到達 = タイマーの停止のみ。自動でコースを終了させない
- コースの終了は**スタッフの明示的な操作**で行う
- Main 画面は0秒到達を表示しつつ、スコアの更新も反映し続ける

「タイマーが0になったら締める」という実装にすると、最後の1問の判定を入力できなくなる。

### 4.3 早押しプレーオフ

各コースの判定基準の最終手段。判定対象者のみで行い、**1問正解で勝ち抜け・1問誤答で敗退**。

4コース共通で使える独立モードとして実装する。ルールが単純なため、コース本体より実装は軽い。

#### 同着の検出はシステムが行う

判定基準でソートした結果、**残り枠の境界線上に複数名が並んだ場合**にプレーオフが必要になる。この検出をシステムが行い、対象者を提示する。

```
1. コース終了時（15分経過）、判定基準でソートする
2. 残り枠数を n とする
3. n 位と n+1 位が判定基準で完全に同値なら、その同値グループがプレーオフ対象
4. 対象者を Admin / Main に提示し、プレーオフモードへ移行する
```

#### プレーオフを行うのは15分経過のときだけ（改訂）

当初は「3名失格 or 15分経過」の両方でプレーオフを行うとしていたが、**3名失格のケースは席順で決着させる**ことにした。

理由は、この2つで**同点が持つ意味の重さが違う**ため。

| 終了条件 | 同点が決めるもの |
|---|---|
| 3名失格（条件2） | 残った全員がどのみち勝ち抜ける。**順位の付け方だけ**の問題 |
| 15分経過（条件3） | **誰が通過するか**が決まる |

前者でプレーオフを行うのは、通過者が変わらない場面で会場の時間を使うことになる。したがって条件2 の順位は次で決める。

```
判定基準（ポイント多い順など）→ 同点なら席順
```

席順＝コース選択と同じ優先順位（**2nd Round 勝ち抜け順 → 1st Round 順位**）。これは全選手でユニークなので、必ず決着する。

ただし**通過順位は準決勝の席順（5章）に直結する**ため、順位そのものは正しく付ける必要がある。「残り全員が勝ち抜けだから順序はどうでもよい」わけではない。

**2nd Round との重要な違い:** 2nd Round の判定基準は最後が「1st Round 順位」で、これは全選手でユニークなため**同着が原理的に発生しない**。3rd Round は最後がプレーオフである以上、判定基準だけでは決着しないケースが実際に起こりうる。同着検出は必須の機能であり、省略できない。

## 5. 準決勝への引き継ぎ

### 5.1 通過順位

「実施したコースの順 → コース内の順位」でソートして 1〜8位を確定する。

コース実施順を使うため、**実施順を永続化する必要がある**。

### 5.2 席順

準決勝は9席。3rd Round 通過の8名を、通過順位の順に以下の席へ配置する。

| 通過順位 | 席（左から） |
|---|---|
| 1位 | 4番目 |
| 2位 | 6番目 |
| 3位 | 3番目 |
| 4位 | 7番目 |
| 5位 | 2番目 |
| 6位 | 8番目 |
| 7位 | 1番目 |
| 8位 | 9番目 |

```ts
const SEMIFINAL_SEATS = [4, 6, 3, 7, 2, 8, 1, 9];
```

8席が重複なく埋まり、**空くのは中央の5番席のみ**。ここが Extra Round の敗者復活者の席になるものと推定している（要確認）。

上位ほど中央寄りに配置される構造になっている。

## 6. データの持ち場所

既存の方針（進行状態はサーバメモリ、結果は DB）を踏襲する。

### 6.1 サーバメモリ（`server/ThirdRoundHandler.js`）

揮発してよい進行状態。

```js
let thirdRoundState = {
    phase: "courseSelect",  // "courseSelect" | "quiz" | "playoff"
    step: "entry",          // phase=courseSelect のとき: "entry" | "closed"
    quizOrder: 1,           // phase=quiz / playoff のとき: 何番目のコースか
    finishedOrder: null     // コース終了処理を走らせたコースの quizOrder
};
```

コース選択フェーズは「抽選 → エントリー」の2ステップを4回繰り返す。`step` に `"assign"` を設けないのは、確定済みかどうかを DB から判定できるため（6.1 冒頭の方針どおり、導出できるものは持たない）。

`phase` に `"playoff"` を設けたのは、**プレーオフ中であることが導出できない**ため。プレーオフの対象者そのものは `thirdRoundRank === 0` で導出できるが、コース進行中も未決着の選手は `rank === 0` なので、状態を見ないと区別がつかない。`quizOrder` はそのまま使うので、どのコースのプレーオフかは分かる。

`finishedOrder` も同じ理由で持つ。「コース終了処理を走らせたか」は結果から復元できない。終了後は `rank === 0` の選手が互いに同値になるが、**コース開始直後も全員が同値**なので区別できない。`quizOrder` と比較する形にしているため、コースごとに持つ必要はない。

これに加えて次を保持する。

- 15分タイマーの残り秒数（**コースごと**）と、いま走っているコースの `quizOrder`

タイマーをコースごとに持つのは、次のコースへ移ったときにリセットを忘れると前のコースの残り時間で進行してしまうため。ただし**動かすのは常に1本だけ**にする。コースごとにインターバルを持つと「別のコースに移ったのに前の時計が回りっぱなし」という事故が起こりうる。`quizOrder` か `phase` が変わったら自動で停止する。

エントリータイムのタイマーは持たない（BGM で管理するため。2.5 参照）。

### 6.2 DB

復元が必要な結果。

**リスク:** サーバを再起動するとタイマーと進行状態が失われる。スコアは DB にあるため復旧可能だが、タイマーは手動で復元することになる。2nd Round も同じ割り切りなので許容するが、15分という長さを考えると 3rd Round の方が影響は大きい。

### 6.3 スキーマ（確定）

#### Player に追加するフィールド

| フィールド | 型 | 用途 |
|---|---|---|
| `thirdRoundCourseName` | `String?` | 所属コース名。`ThirdRoundCourse.name` への外部キー |
| `thirdRoundCorrectCount` | `Int @default(0)` | 正解数（**4コース共通で加算する**。下記） |
| `thirdRoundWrongCount` | `Int @default(0)` | 誤答回数（全コース） |
| `thirdRoundUpDownPoint` | `Int @default(0)` | 10 up-down の現在ポイント |
| `thirdRoundSwedishCross` | `Int @default(0)` | Swedish 10 の × の数 |
| `thirdRoundFreezeRest` | `Int @default(0)` | Freeze 10 の残り休み問数 |
| `thirdRoundRank` | `Int @default(0)` | 勝抜→正の数、失格→−1、未決着→0 |

`thirdRoundRank` の規約は `secondRoundRank` と揃える。

**命名について:** 単一コースでしか使わない3つのフィールドには、コース名を含めた。`thirdRoundPoint` のような汎用名だと、10 by 10 の「総合ポイント」と混同される。`secondRoundCorrectCount` が実際にはポイントだった件と同じ失敗を避けるための措置である。

**リレーションについて:** 参照先を `ThirdRoundCourse.name` にしたため、`Player` には**コース名の文字列がそのまま入る**。表示のために `include` を書く必要はない。参照先を `id` にすると数値しか残らず、名前を出すたびに `include` が必要になる。

#### 列を持つ / 持たないの判断

| 値 | 判断 | 理由 |
|---|---|---|
| 10by10 の総合pt・誤答pt | **持たない** | `正解数 × (10 − 誤答数)` で導出できる |
| 10up-down のポイント | **持つ** | 誤答で0に戻るため正解数から導出できない |
| Swedish の × | **持つ** | 誤答時点の正解数に依存するため履歴なしでは導出できない |
| Freeze の残り休み | **持つ** | 出題の進行に依存するため導出できない |
| スルー回数 | **持たない** | 休みを減らす契機に使うだけで、選手に紐づく値ではない |
| プレーオフの対象者 | **持たない** | コース終了処理で決着した人には順位が入るため、`thirdRoundRank === 0` で導出できる |
| コース終了処理を走らせたか | **持つ**（サーバのメモリ） | 終了後は `rank === 0` の選手が互いに同値になるが、コース開始直後も全員が同値なので区別がつかない |

導出できるものは列にしない。二重管理を避けるための原則とする。

#### `thirdRoundCorrectCount` は4コース共通で加算する（改訂）

3.2 に「10 up-down は累計正解数を保持する必要はない」と書いたが、これは**専用の列を作る必要がない**という意味であり、既にある共有列に書かないという意味ではない。

共通部分に1コースだけ例外を作るより、「**共通処理は常に同じことをして、コース別のルールは足すだけ**」という形を保つ方が、コースを増やすときに追いやすい。正解数はポイントから導出できない（誤答で0に戻るため）ので、記録として残す価値もある。

ただし**データを持つことと画面に出すことは別**。10 up-down の表示はポイントにする。誤答で0に戻るポイントの横に戻らない正解数を並べると、「⭕️7 なのに勝ち抜けまで残り3問ではない」という誤読を招く。

#### コース情報

実施順を持つため、4行のテーブルを作る。

```prisma
model ThirdRoundCourse {
  id        Int      @id @default(autoincrement())
  name      String   @unique
  playOrder Int?     // 抽選で決まる実施順 1〜4。抽選前は null
  players   Player[] // Prisma の文法上必須。DBの列にはならない
}
```

`playOrder` を nullable にしているのは、**抽選前と抽選後を区別するため**である。実施順をシステムが抽選する以上、「まだ引いていない」状態が存在する。0 やダミー値で代用すると、抽選済みかどうかを判定できなくなる。

Player に `thirdRoundCourseOrder` を持たせる案（非正規化）もあるが、実施順がコースの属性である以上、コース側に持たせる方が素直である。

`status` 列は**持たない**。「今どのコースが進行中か」は `currentMode` や `secondRoundState` と同じ進行状態であり、このアプリでは一貫してサーバのメモリで管理している。ここだけ DB に入れると方針がぶれる。

#### 4行の投入方法

コース4行は**マイグレーションの `INSERT` で投入する**。

- seed に置くと `NODE_ENV=production` のガードに阻まれ、本番構成では作れない
- 抽選時に `upsert` する案もあるが、抽選前にコース一覧を DB から読めなくなる（ルーレット演出は抽選前に4コースを表示する）

コース名は `lib/thirdRoundCourses.ts` の定数と一致させる。採点ロジックがコース名で分岐するため、コード側にも同じ文字列が必要になる。

#### Match モデルの削除

`Match` はどこからも参照されておらず、進行状態はサーバのメモリで管理していたため削除する。準決勝以降で「今どのセットか」を持ちたくなった場合も、同じ理由でメモリ管理になる見込みである。

#### Undo 用の履歴

2nd Round で有効だったスナップショット方式を踏襲する。

```prisma
model ThirdRoundHistory {
  id        Int      @id @default(autoincrement())
  createdAt DateTime @default(now())
  course    String   // どのコースの履歴か
  snapshot  String   // そのコースの5名分の JSON スナップショット
}
```

2nd Round では**スナップショットを取るタイミングのバグ**で Undo が壊れていた。3rd Round でも同じ轍を踏まないよう、状態を書き換える前に文字列化することを設計時点で明記しておく。

## 7. 画面構成

### Main（会場投影）

| 状態 | 表示内容 |
|---|---|
| `courseSelect` / `draw` | ルーレット演出 → 確定したコース名 |
| `courseSelect` / `entry`（締切前） | コース名 / 参加者20名 |
| `courseSelect` / `entry`（確定後） | 出場者5名 |
| `quiz` | 出場5名のスコア / 15分タイマー / コース別の状態（休み・×など） |
| `playoff` | 出場5名。勝ち抜け・敗退・プレーオフ対象を色で区別する（下記） |

Main は独自の状態を持たない。配信された `thirdRoundState` と選手データだけで表示が決まる。

#### プレーオフ画面も5名全員を出す（改訂）

当初は「対象者のみ表示」としていたが、**5名全員を表示する**ことにした。

プレーオフの対象者は状態として保存せず、`thirdRoundRank === 0` で絞って導出している。この方式には利点がある一方で、対象者だけを画面に出すと**勝ち抜けた瞬間にその選手が一覧から外れ、画面から消える**。会場から見ると、勝った瞬間が分からないままカードが1枚ずつ減っていくことになる。

5名全員を出し、順位フィールドで見た目を分ける。

| `thirdRoundRank` | 見た目 |
|---|---|
| 正の数（勝ち抜け） | 金色・拡大・`👑 WIN（N位）`。**コース本体の勝ち抜けと同じ** |
| −1（敗退） | グレーアウト。失格条件を満たしていれば `OUT`、時間切れなら `敗退` |
| 0（プレーオフ対象） | 紫の枠で強調 |

こうするとプレーオフで勝った選手はその場で紫から金色に変わって残り、コース本体で勝ち抜けた選手と同じ見え方になる。**「対象者を状態として持たない」という設計はそのまま維持できる。**

### Admin（進行卓）

| 状態 | 操作 |
|---|---|
| `courseSelect` / `draw` | 抽選する / 抽選をリセット |
| `courseSelect` / `entry` | エントリー締切 → 掲げた人のチェック → 出場者を確定 → 次のコースの抽選へ |
| `quiz` | 正解 / 誤答 / **スルー（Freeze 10 のみ）** / Undo / タイマー操作 / コース終了 / プレーオフへ |
| `playoff` | 正解 / 誤答 / Undo |

2nd Round との差分は **スルーボタン**（Freeze 10 限定）、**タイマー操作**、**コース終了の明示操作**。

コース終了ボタンは**残り時間が0のときだけ表示する**。終了条件1（2名勝ち抜け）と条件2（3名失格）は自動で決着するため、この操作が要るのは条件3（15分経過）だけだから。

その裏返しとして、タイマーを開始し忘れると終了ボタンが一度も出なくなる。復旧のため**残り時間の手動編集**を用意している（疑義の申し立てで時間を戻す場合にも使う）。

「プレーオフへ」は**コース終了処理を走らせ、かつ判定基準で決着しなかったとき**だけ出す。移行は明示操作にする。会場では司会の進行が入るため、システムが勝手に画面を切り替えるとタイミングが合わない。

Admin は抽選直後から確定したコースを見られる。会場に伏せる必要があるのは Main だけで、進行卓は次に何が来るかを知らないと準備できない。

## 8. 決定事項

| # | 項目 | 決定 |
|---|---|---|
| 1 | 5番席 | 中央の空席は Extra Round 敗者復活者の席。3rd Round 通過者は5番席に座らない |
| 2 | スルーの扱い | **Freeze 10 のみ記録する。** 他コースではスルーボタンを表示しない |
| 3 | コース実施順 | **システム上で抽選する。** ルーレット演出付き（アニメーションは第2段階） |
| 7 | 抽選の粒度 | **1回の抽選で1コースだけ決める。** 抽選とエントリーを4回繰り返す |
| 8 | フェーズの順序 | **20名全員の所属を確定させてから**、クイズ実施に入る |
| 9 | エントリータイマー | **作らない。** 専用BGMで計測し、Admin の「締切」ボタンでチェック欄を開く |
| 10 | エントリーと確定 | **同じ画面**で行う。確定済みかは割当済み選手数から判定する |
| 4 | プレーオフの発生判定 | **同着の検出はシステムが行い**、対象者を提示する。**プレーオフは15分経過のときだけ**行い、3名失格のケースは席順で決着させる（4.3 参照） |
| 5 | 15分タイマー | **0秒到達後も操作を受け付ける。** コース終了はスタッフの明示操作 |
| 6 | 連答権 | **3rd Round に連答権は存在しない。** 2nd Round のような連答処理は不要 |

### 連答権がないことの含意

2nd Round のスコア更新で最も複雑だったのは連答権の管理（保持者の特定、他者への波及、解消条件の分岐）だった。3rd Round にはこれが存在しないため、**1人の操作が他の選手の状態に波及するのは Freeze 10 の休みカウントだけ**になる。

ただしその Freeze 10 は、逆に2nd Round にはなかった「全員に対する毎問の減算」を持つ。波及の方向が違うだけで、単純にはならない点に注意する。

## 付録: 検算済みの事項

以下は設計時に機械的に確認済み。

- 10 by 10 の必要正解数表と、誤答0〜5回のすべてから勝ち抜けに到達可能であること
- Swedish 10 の × 加算表が正解数0〜9を網羅していること、失格までの最短が3誤答であること
- Freeze 10 の休み累計問数
- 「3名失格」と「残り人数＝残り枠」が同値であること
- 席順 `[4,6,3,7,2,8,1,9]` が9席のうち8席を重複なく埋め、5番席のみが空くこと
