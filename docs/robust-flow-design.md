# 画面遷移・待機画面まわりの堅牢化（2026-11-04〜05）

ブランチ: `feature/robust-flow`。目的は「運営者が意図した操作が、意図した状況になること」と「大会中に止まらない・戻せること」。
きっかけは、待機画面の追加で手動の画面遷移が壊れたこと。そこで、操作しうるパターンを洗い出し、仕組みごと作り直した。

## 1. 原因

状態がいくつもの箱（モード・各ラウンドの進行・覆い・問題番号）に分かれ、Admin のブラウザがそれぞれを別々に書き換えていた。
そのため次の問題が起きた。

- 画面が後から現れたとき（覆いが外れた直後など）、今の状態を取りに行かない
- 覆いと進行が別の状態で、Undo や手動切替で食い違う
- 同じ操作が二重に効く（連打・二人の Admin・古い画面）
- サーバの再起動で進行状態がすべて初期値に戻る
- 切断中に押した操作が、つながった瞬間にまとめて実行される

## 3. 設計

### 3-1. 覆いの遷移表（`lib/coverFlow.js`。サーバと Admin が共通で使う純関数）

覆いは6つの形に限る。

| 記号 | 形 |
|---|---|
| N | なし（ラウンドの画面を出す） |
| BS | ブランク・これから始まる場面 |
| BE | ブランク・早押しが終わった後 |
| SS | 待機画面 NEXT ○○・これから |
| SE | 待機画面 NEXT ○○・終わった後 |
| M | 手動の PLEASE STAND BY（割り込み） |

許される遷移は表に書いてある。表にない遷移は受け付けない。

- 要求には、Admin が見ていた**版番号（rev）**を添える。サーバの版と違えば断る。
- M は「割り込み」。外すと、割り込む前の覆いに必ず戻る。
- どの覆いからでも、**強制解除**で N に戻れる（行き止まりがない）。
- ラウンドの切替で、サーバが覆いを自動で決める。覆いを先に配り、そのあとにモードを配る（覆いなしでラウンドの画面が一瞬出ない）。

### 3-2. 保存と復元（`server/stateStore.js`）

- 各ハンドラが `register(名前, 保存する値, 戻す処理)` を1回書く。
- 操作の直後（200ms まとめ）と1秒ごとに、変わっていれば `.state/server-state.json` へ書く。一時ファイルに書いてから置き換える。
- 読めないファイルは `.corrupt-時刻` に退避して初期値で起動する。項目ごとに検証し、不正な項目だけ捨てる。
- タイマーは**止めた状態**で戻す。再起動の間の時間は数えない。
- `.state/` は git に含めない。選手の個人情報は入っていない。

### 3-3. 画面側

- `useSocketSync` … 表示した時とつなぎ直した時に `request_*` を送る。
- `useMainCover` … 版つきの要求。断られたら理由を出す。
- `AdminNoticeHost` … 接続切れの帯と、通知。
- `createAdminSocket` … 切断中の操作を捨てる。
- `useSingleFlight` … 処理中は次を受け付けない。
- 進行ボタンは押した直後 0.7 秒押せなくする。覆いの変更は 0.45 秒以内の次の要求を捨てる。

## 4. 方式の比較（選んだ案に ◎）

### a. 二重実行の防ぎ方

| 案 | メリット | デメリット |
|---|---|---|
| ◎ 版番号の照合（楽観ロック）＋押した直後の無効化 | 連打・二人の Admin・古い画面を、サーバ側で確実に断れる。仕組みが小さい | 版番号は「画面が更新された後の押し直し」は防げない。そのため無効化を併用する必要がある |
| 操作ごとの ID（冪等キー） | 通信の再送も安全に扱える | 全操作に ID を付ける改修が大きい。同じ内容を意図して2回押す操作と区別しにくい |
| 全操作をサーバの状態機械に移す | 最も堅牢で、画面は表示だけになる | 全ラウンドの書き直しに近い。大会までの時間では危険 |

### b. 進行状態の保存先

| 案 | メリット | デメリット |
|---|---|---|
| ◎ JSON ファイル | 追加の依存がない。壊れても退避して起動できる。DB のスキーマを変えない | 書き込みはサーバ1台前提。複数台構成には使えない |
| DB（SQLite）の1行 | 結果と同じ場所にあり、一貫性を取りやすい | スキーマ変更（migrate）が要る。サーバ側が Prisma を使えない構造（CommonJS）なので手間が大きい |
| メモリのみ（従来） | 簡単 | 再起動で全部消える |

### c. 切断中の操作

| 案 | メリット | デメリット |
|---|---|---|
| ◎ 捨てて知らせる | つながった瞬間の暴発がない。運営者は画面で状況を確かめてからやり直せる | 押した操作は失われる（が、何も起きていないことは表示される） |
| ためて、つながったら送る（従来） | 操作が失われない | 押し直した分も含め、まとめて実行される。画面が何段も進む |
| ためて、つながったら確認を出す | 失われず暴発もしない | 実装が重い。確認を読む余裕が当日あるか不明 |

### d. 引き出し（手動切替）を使ったときの覆い

| 案 | メリット | デメリット |
|---|---|---|
| ◎ 覆いは変えない | 会場に意図しない画面が出ない | 覆いを外すまで、選んだ画面は会場に出ない（上のバーに覆いの状況が出る。急ぐときは「覆いを外す」） |
| 覆いを外して選んだ画面をすぐ出す | 押した結果がすぐ見える | 誤タップがそのまま会場に出る |

### e. 終了後に Undo したときの Main

| 案 | メリット | デメリット |
|---|---|---|
| ◎ ブランクにして「クイズを再開する ▶」 | 戻した画面をいきなり会場に出さない。既存のブランクの仕組みで足りる | 再開に1手増える |
| 自動で本編に戻して出す | 1手少ない | 戻した瞬間の途中の画面が会場に出る |

### f. 選手データの配信の持ち主

| 案 | メリット | デメリット |
|---|---|---|
| ◎ ブラウザが中継（従来）＋つなぎ直したら DB から読み直す | API を変えずに済む。DB なしでは動作確認できない部分に触れない | 「DB は更新済みだが中継が失われた」瞬間は残る。再読み込み（またはつなぎ直し）で追いつく |
| API が直接サーバから配信する | 根本解決。ブラウザの切断に影響されない | 約20の API を変える。DB なしでは動作確認できず、今回は実機の確認ができない |

## 5. 「一本道」と各ラウンド・各セットの独立

結論: **一本道のまま、ラウンド・セットごとの独立を強めた**。

- **一本道が原因だった部分**: 次の組・コースへ進む操作が、裏で組・コースの切替と覆いの切替を同時に行うため、Undo が新しい組・コースに効いていた（B2）。
- **独立にした部分**:
  - 各ラウンドの状態は別の箱として保存・復元する
  - 結果が入っているラウンドへ戻るときは、その場面の続きとして扱う（B4）
  - Undo は組・コース単位の記録で、前の組・コースまで戻れる
- **独立にしなかった部分**:
  - 覆いは全体で1つ。会場の画面は1つなので、ラウンドごとに持つと矛盾する
  - 進行の順序（前のラウンドが終わるまで次へ進めない）は維持した。当日1人で操作するので、順序の強制は誤操作を防ぐ
- **案の比較**:
  - 全ラウンドを自由に行き来できる独立モード … 柔軟だが、「この場面は今どこ？」を運営者が常に管理することになり、1人運営では誤操作が増える
  - 一本道＋途中の脱出口（強制解除・手動切替・resume・Undo の巻き戻し）… 通常は迷わず、困ったときだけ手動 ◎
