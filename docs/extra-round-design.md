# Extra Round 設計メモ

敗退者全員 → 1人。敗者復活者は準決勝の5番席に入る。

このメモは実装前の設計合意を目的とする。ルールの出典は `abc the24th ルール` の Extra Round 節（PDF は `docs/` にあるが `.gitignore` 済み）。

3rd Round との最大の違いは、**参加者がシステムに入っていないこと**だった。この前提が変わるため、1章で先に移行の話をする。

---

## 0. 実装済みの仕様（2026-10-06）— 3.4・3.5・6章より優先

実装時にユーザーと詰めた内容。**以下は 3.4（進行状態）・3.5（Main の表示）・6章（画面構成）の旧案を置き換える。** 旧案の記述は経緯として残している。

### 進行状態（`server/ExtraRoundHandler.js`、メモリ保持）

```js
{ stage: "setup" | "firstStep" | "entrantSelect" | "secondStep", cursor: 0..39, revealed: boolean }
```

- `cursor` は First Step の「いま何を出しているか」。40ステップの並びは `lib/extraRound.ts` の `FIRST_STEP_SEQUENCE`。問題番号・出題/解答・フェーズ・進出者決定ボタンを出す位置はすべて `cursor` から導出する（別々に持たない）
- 並び順: 問題1〜10 → 解答1〜10 → 問題11〜15 → 解答11〜15 → 問題16〜20 → 解答16〜20
- Admin から届く値はサーバ側で検証する（未知の `stage` は無視、`cursor` は整数で 0〜39 に丸める）
- `revealed`（2026-10-07 追加）: 「いまのステップの問題文／解答を Main に出したか」。`false` のとき Main は枠だけ表示し、Admin が「問題を表示する」「解答を表示」を押すと `true` になり、Main で問題文・解答とも全体が一度に現れる（下の「表示アニメーション」参照）
- サーバ再起動で `stage: "setup"` に戻る。Admin の「手動操作」から段階を選び直せる（登録済みの問題は DB にあるので「登録済みの問題を使う」で再開できる）

### 画面の流れ

| stage | Main | Admin |
|---|---|---|
| `setup` | 「準備中」 | 問題CSVの取込（登録済みの問題を使うボタンあり）。取込成功で `firstStep` へ |
| `firstStep` | 問題 → 解答の順に1つずつ（解答のときは問題文と解答を同時表示）。ステップが変わった直後は枠だけで、Admin の表示ボタンで文字が現れる | 「問題を表示する ▶」→「次へ」（解答ステップは「解答を表示 ▶」）の1本道ボタン。解答10・15・20 の地点では「2nd Step 進出者決定」を出し、解答10・15では「次のフェーズに進む」も出す（解答20の後は問題が無いので出さない） |
| `entrantSelect` | 「準備中」 | 通過者の選択（検索＋チェック、最大12名）。「2nd Step に進む」で確定 |
| `secondStep` | 2nd / 3rd Round と同じ縦長カード（`PlayerCardFrame`）。サブタイトルは `Second Step 5○1×`。正解数は数字のみ（○・の並びは出さない） | 「進行中...」表示（勝者確定後は完了表示）。選手名ボックスは最長の名前に合わせて全員同じ高さ。採点（正解・誤答）。Undo と結果リセットは「手動操作」 |

### 表示アニメーション（問題文・解答の段階表示）

- Main の見出しは `QUESTION N` のみ（「第○問：」「第 N〜M 問」は出さない）。右上は `Phase N` だけ
- Socket.IO: Admin → サーバ `reveal_extra_round_step` `{ cursor }`、サーバ → 全員 `update_extra_round_state`（既存）。`change_extra_round_state` で `cursor`／`stage` が変わると、`revealed` を明示しない限り **`false` に戻る**（誤って答えを先に出さないための安全側の既定）
- `reveal_extra_round_step` は「`stage === firstStep` かつ `cursor` が現在値と一致 かつ まだ `revealed === false`」のときだけ有効。古い Admin 画面の押し間違い・二重送信は無視される
- 「戻る」は `revealed: true` で送る（一度見せた内容を再アニメーションせず即表示）。次へ／ジャンプ／フェーズ移動／最初・最後へ／CSV取込直後は `revealed: false`
- Admin の「次へ」「表示」ボタンは 800ms のクリックガード付き（同じ位置で表示ボタン→次へボタンに入れ替わるため、ダブルクリックで1問飛ばすのを防ぐ。`CLICK_GUARD_MS`）
- 旧サーバ（`revealed` を送らない）対策として、Main/Admin は `normalizeExtraRoundState` で `revealed` 欠落時を `true`（表示済み）として扱う
- Main は「マウント中に `false → true` を観測したときだけ」アニメーションする。途中で開いた／リロードした Main は、表示済みなら即座に全文表示する（`app/components/Main/RevealText.tsx`）
- 1文字ずつの `span`（opacity／blur／位置）で描画し、禁則処理・折り返しを保つ。未表示中は `visibility:hidden` の同一テキストで枠サイズを固定（表示の瞬間にレイアウトが動かない）。文字分割は `Intl.Segmenter`（絵文字・結合文字を1文字として扱う）。速度は文字数で自動調整（問題文は最大 1文字75ms／全体4秒、解答は最大 1文字140ms／全体2.5秒。`lib/revealText.ts`）
- 2026-10-11 のユーザー指示で、問題文・解答・別解はすべて全体が一度に現れる（`RevealWhole`。ぼかし＋少し下からせり上がり、0.7秒。文字色は変えない）。解答と別解は同時に現れる
- Admin の MAIN カードに「問題文はまだ出していません」「問題文のみ表示中・解答はまだ出していません」を表示。表示前は次ステップの「〇〇を表示する」ボタンを押せない状態で見せる

### 問題CSV

- 列: 1列目 問題番号 / 2列目 問題文 / 3列目 模範解答 / 4列目 別解・正誤判定基準（空でも可）。見出し行・BOM・CRLF・引用符つきセル（カンマ・改行入り）に対応（`lib/extraRoundCsv.ts`）
- 1〜20問がすべて揃っていないと取り込めない（欠け・重複・範囲外・空の問題文／解答はエラー表示）。画面と API の両方で同じ検証をする
- 別解・正誤判定基準は Admin に加え、2026-10-11 のユーザー指示で Main の解答ステップにも出す（解答と同時に全体一度に現れる。空なら出さない）。Main 用の取得（`GET /api/extraRound/questions?public=1`）にも含める
- DB: `ExtraRoundQuestion.altAnswer`（マイグレーション `20261006120000_add_extra_round_question_alt_answer`）

### 進出者の確定（`POST /api/extraRound/secondStepEntrants`）

- 1〜12名。3rd Round 通過者・存在しない選手・13名以上・0名は 400
- 選択画面の候補一覧と選択済みの並びは**ペーパー順位（`paperRank`）の昇順**（2026-10-10、ユーザー指定）。順位未設定は末尾、同順位はエントリーナンバー順
- **1名だけ選んだ場合は Second Step を飛ばし、その1名を敗者復活（`extraRoundRank = 1`）として確定**（確認ダイアログあり）。準決勝5番席には `extraRoundRank === 1` から自動で入る
- すでに Second Step の採点結果・履歴があるときに選び直すと 409。画面の確認後に `confirmReset: true` で再送すると、Extra Round の結果と履歴を初期化して登録する（準決勝が始まっている場合は確認文を強める）

### Second Step の採点（`POST /api/extraRound/secondStep/updateScore`）

- 出場者以外・結果確定済みの選手・勝ち抜け者が決まった後の操作は 400（何も変わらない履歴が積まれて Undo がずれるのを防ぐ）
- ルールは `lib/extraRoundScoring.ts`（5問正解で勝ち抜け／誤答は即失格／残り1名で自動勝ち抜け）

### デザイン

- Main: `FixedStage`（1920×1080）。カードは `app/components/Main/PlayerCardFrame.tsx`（3rd Round から切り出した共通部品）。勝者は「WIN」、失格は「LOST」
- Admin: 3rd Round Admin と同じ構成（上部の1本道ボタン＋折りたたみの「手動操作」＋黒い本体パネル）。共通スタイルは `app/components/Admin/adminCyberStyles.ts`
- Design アーティファクトに Main 4枚（準備中／問題／解答／Second Step）と Admin 4枚（取込／First Step／進出者選択／Second Step）を追加済み（実画面を取り込んだもの）

## 1. 前提: 参加者は約200名

Extra Round は「準決勝進出の8名を除いた、これまでの敗退者全員」で行う。**1st Round で48位に入らなかった人も含む**ので、対象は約200名になる。

ところが現在の DB には**1st Round 上位48名しか入っていない**。CSV 取込がそういう作りになっている。このままでは、敗者復活した人が DB に存在しない可能性がある。

### 決定: 1st Round 参加者全員を DB に入れる

取り込む対象を上位48名から全員（約200名）に変える。こうすると Second Step の参加者を**既存のレコードから選ぶだけ**で済み、その場で名前を打ち込む必要がなくなる。本番の進行中に人名を手入力するのは避けたい。

### 1.1 影響する箇所

| # | 箇所 | 200名にすると |
|---|---|---|
| 1 | 2nd Round の組分け（画面側） | `paperRank % 4` で絞るだけなので各組が12名 → **50名**になる |
| 2 | 2nd Round の組分け（API 側） | 取込時に全員へ `secondRoundGroupNumber` を付けているので同上 |
| 3 | `resetScores` | 組で絞っているので 2 と同時に直れば解決する |
| 4 | 1st Round の CSV 取込 | 200行を1件ずつ `create` している。`createMany` に変えたい |
| 5 | `loadPlayers` と Socket 配信 | 毎回200名分を配る。数十KB程度の見込みだが実測する |

3rd Round は `secondRoundRank >= 1` で20名に絞っているため**影響しない**。

### 1.2 組分けの二重管理を先に直す

調査で既存の問題が見つかった。**組分けが2通りの方法で表現されている。**

```
画面（AdminSecondRound / MainSecondRound）  … paperRank % 4 を毎回計算する
API（updateScores / resetScores / undo）    … secondRoundGroupNumber 列を見る
```

48名なら両者は必ず一致するので表面化していなかったが、200名にすると両方を直す必要がある。

**決定: 列を正とする。** 取込時に**上位48名だけ** `secondRoundGroupNumber` を付け、49位以降は `null` にする。画面側も `paperRank % 4` の計算をやめて列を見る。

組番号は `paperRank` から導出**できる**値だが、「48名までしか 2nd Round に出ない」という条件が付くと単純な導出ではなくなる。列に入れておけば、その判断が**取込の1箇所に閉じる**。「2nd Round に出るか」が列の有無で表現でき、200名を混ぜても画面が壊れない。

アドバンテージ（`secondRoundPoint`）も同じく上位48名だけに設定する。`getAdvantage` は49位以降に0を返すので実害はないが、意味のない値を全員に書かない方がよい。

## 2. 全体の流れ

```
敗退者全員（約200名）
    ↓
[First Step] 筆記クイズ・最大3フェーズ
    フェーズ1    1〜10問  → まとめて正解発表 → 正解数を確認
    フェーズ2    11〜15問 → まとめて正解発表 → 順位を確認
    サバイバル   16問目以降を1問ずつ、誤答・無解答で即着席
    ↓
    通過者 1〜12名
    ↓（通過者が1名なら、その時点で敗者復活が確定し Second Step は行わない）
[Second Step] 最大12名の早押し
    5問正解で敗者復活。誤答は即失格
    ↓
    敗者復活者 1名 → 準決勝の5番席
```

**Second Step を行わない場合がある。** 各フェーズでトップが1名なら、そこで敗者復活が決まる。

## 3. First Step

### 3.1 ルール

すべてのフェーズで筆記クイズを行う。読み上げで出題し、シンキングタイムは**問題文を2回読んだあと5秒**。解答者は起立した状態で解答用紙に記入する。

#### フェーズ1（1〜10問）

10問を続けて出題し、終了後に**10問の正解をまとめて発表**する。その後、正解数を確認する。

| トップタイの人数 | 処理 |
|---|---|
| 1名 | **その者が敗者復活**（Second Step を行わない） |
| 2〜12名 | 全員 First Step 通過 → Second Step へ |
| 13名以上 | 該当者のみフェーズ2へ |

#### フェーズ2（11〜15問）

5問を続けて出題し、終了後に**5問の正解をまとめて発表**する。

順位は次で決める。

1. 正解数の多い方が上位
2. 同じ正解数なら、**全15問を通して最初に誤答した問題番号が大きい方**（はじめて誤答したのが遅い方）が上位

分岐はフェーズ1 と同じ（1名 / 2〜12名 / 13名以上）。13名以上ならサバイバルフェーズへ。

#### サバイバルフェーズ（16問目以降）

1問ずつ出題し、シンキングタイム終了後**すぐに正解を発表**する。

- 誤答・無解答となった参加者はその問題の時点で失格となり着席する
- 連続正解している参加者が**12名以下になったとき**、残っていた参加者を通過とする
- ある問題で**全員が着席した場合**、その問題で着席した人を起立させて続行する
- **1名を除いて全員が着席**した場合、その者が敗者復活
- 20問目を終えて13名以上残っている場合、**1st Round の成績で12名を決定**する

以上により、1名以上の通過者が必ず決まる。

### 3.2 システムの役割は表示だけ（決定）

**採点はシステムの外で行う。** システムがやるのは次の2つに限る。

- 問題文を表示する
- 解答を発表する（フェーズ1・2 はまとめて、サバイバルは1問ずつ）

その後、**First Step 通過者（1〜12名）を Admin で入力**する。

#### なぜ採点を持ち込まないか

約200名 × 10問 = 2000マスの正誤入力になる。フェーズ2 の同点判定に必要な「最初に誤答した問題番号」を出すには問題単位の記録が要るため、正解数だけの入力では足りない。本番の進行中にこの量を捌くのは現実的でない。

ルール上も「First Step の解答はスタッフがチェックを行う」と明記されており、紙での採点が前提になっている。

**結果として、参加者の一覧を画面に出す必要もない。** 誰が残っているかはシステムが知らない。会場では起立・着席で見えている。

### 3.3 問題データ（新規）

**このアプリが初めてクイズの中身を持つ。** 1st〜3rd Round はすべて司会が問題を読み、スタッフが正誤だけ入力する作りだった。DB にあるのは選手と得点だけである。

First Step で問題文と解答を表示するため、問題を DB に持つ。

```prisma
model ExtraRoundQuestion {
  id     Int    @id @default(autoincrement())
  number Int    @unique   // 問題番号 1〜20
  text   String            // 問題文
  answer String            // 正解
}
```

問題番号とフェーズの対応は**導出できる**ので列にしない。

| 番号 | フェーズ |
|---|---|
| 1〜10 | フェーズ1 |
| 11〜15 | フェーズ2 |
| 16〜20 | サバイバル |

**CSV で事前に取り込む。** 1st Round の結果取込と同じ仕組みが流用できる。当日は番号を進めるだけにする。本番の進行中に問題文を打ち込むのは避ける。

#### 未決: CSV の列構成と取込画面

- 列は `番号,問題文,正解` でよいか。読みの併記や別解が要るか
- 取込画面をどこに置くか。1st Round のアップロード画面に同居させるか、別に作るか
- 20問を超える場合があるか（サバイバルは20問目で打ち切りなので、上限は20問と読める）

### 3.4 進行状態

`server/ExtraRoundHandler.js`（新規）のメモリに持つ。揮発してよい。

```js
let extraRoundState = {
    step: "firstStep",       // "firstStep" | "secondStep"
    questionNumber: 1,       // 現在の問題番号 1〜20
    view: "question"         // "question"（出題中） | "answers"（解答発表中）
};
```

**フェーズ（phase1 / phase2 / survival）は持たない。** `questionNumber` から導出できる。

**「何名が残っているか」も持たない。** 採点をシステム外で行うため、そもそもシステムが知らない。

### 3.5 Main の表示（決定）

進行に合わせて次を切り替える。

| `view` | 表示 |
|---|---|
| `question` | 現在の問題文 |
| `answers` | 問題文と解答のセット |

`answers` のとき、フェーズ1 なら1〜10問、フェーズ2 なら11〜15問を**一覧で**出す。ルールが「まとめて発表する」としているため。サバイバルは1問ずつなので、その問題だけを出す。

## 4. Second Step

### 4.1 ルール

First Step 通過者（最大12名）による早押しクイズ。

- **最初に5問正解した1名が敗者復活**
- **誤答は即失格**
- 1名を除いて全員が失格した場合、残った1名がその時点で敗者復活

### 4.2 3rd Round から流用できるもの

構造は 3rd Round の 10 up-down に近い。「残り人数 ＝ 残り枠」で残りが通過する規則も同じ形で書ける（ここでは枠が1）。

| 3rd Round の部品 | Extra Round で使えるか |
|---|---|
| 純関数に採点を切り出す構造 | **そのまま使う** |
| スナップショット方式の Undo | **そのまま使う** |
| 「残り人数 ＝ 残り枠」の終了判定 | 枠数を1にすれば同じ |
| 順位フィールドの規約（勝抜→正、失格→−1、未決着→0） | **そのまま使う** |

### 4.3 スキーマ

```prisma
// Player に追加
extraRoundCorrectCount Int @default(0)  // Second Step の正解数
extraRoundRank         Int @default(0)  // 敗者復活→1、失格→−1、未決着→0
```

`extraRoundRank` は敗者復活が1名だけなので、正の数は 1 しか入らない。それでも `Boolean` にせず既存の規約に合わせる。3rd Round までと同じ形にしておけば、準決勝の進出者を集めるときに条件を統一できる。

**First Step の通過を表す列は作らない。** Second Step に出るかどうかは、`extraRoundRank` を持つ選手の集合ではなく「Admin が選んだ12名」で決まる。これは進行状態なので DB ではなくサーバのメモリに置く……**が、ここは未決**（下記）。

#### 未決: First Step 通過者をどこに持つか

- サーバのメモリに置く → 再起動で消える。Second Step の途中で再起動すると誰が出ていたか分からなくなる
- DB の列（`extraRoundFirstStepPassed Boolean`）に持つ → 消えないが、「導出できない状態」を列で持つことになる

Second Step は5問正解するまで続くので、進行時間はそれなりに長い。**消えたら困る度合いが高いなら DB** という判断になりそうだが、明日議論する。

### 4.4 参加者の選び方

約200名から最大12名を選ぶ。**検索が要る。** 名前か `entryNo` で絞り込む UI を作る。

3rd Round のエントリー画面は20名固定のグリッドだったので、そのままは流用できない。

## 5. 準決勝への引き継ぎ

**5番席の件はルールで裏付けが取れた。** 3rd Round の設計メモ 5.2 には推定として書いてあったが、確定してよい。

- ルール: 「1名のみが敗者復活となり、準決勝に進出する」
- 準決勝は9名
- 3rd Round 通過8名 + 敗者復活1名 = 9名

3rd Round の席順は `SEMIFINAL_SEATS = [4, 6, 3, 7, 2, 8, 1, 9]` で8席を埋め、**中央の5番席だけが空く**。ここに敗者復活者が入る。

## 6. 画面構成

### Main（会場投影）

| 状態 | 表示内容 |
|---|---|
| First Step / `question` | 問題文 |
| First Step / `answers` | そのフェーズの問題文と解答の一覧 |
| Second Step | 出場者最大12名のスコア（正解数） |

### Admin（進行卓）

| 状態 | 操作 |
|---|---|
| First Step | 次の問題へ / 解答を発表 / 前の問題へ戻る |
| First Step 終了時 | 通過者（1〜12名）を選ぶ |
| Second Step | 正解 / 誤答 / Undo |

## 7. 決定事項

| # | 項目 | 決定 |
|---|---|---|
| 1 | 参加者の範囲 | 準決勝進出の8名を除く全員。**1st Round 参加者約200名を DB に入れる** |
| 2 | 組分けの表現 | **列（`secondRoundGroupNumber`）を正とする。** 上位48名だけに付け、49位以降は null |
| 3 | First Step の採点 | **システム外。** 表示（問題文・解答）と通過者の入力だけを行う |
| 4 | 問題データ | **CSV で事前に取り込み、DB に持つ。** このアプリが初めてクイズの中身を持つ |
| 5 | フェーズ | `questionNumber` から導出する。状態として持たない |
| 6 | 残り人数 | 持たない。採点がシステム外なのでシステムは知らない |
| 7 | 5番席 | 敗者復活者が入る。**ルールで確定**（3rd Round メモの「要確認」を外せる） |
